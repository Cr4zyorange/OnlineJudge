# 设计文档评审与交付边界

来源：`docs/提炼skills/requirements-spec-reviewer.md`、`software-overview-design-reviewer.md`、`software-detailed-design-reviewer.md`，以及 codex skill 的 `design-delivery.md`（采用 `docs/提炼skills/` 最新副本的仓库一致图表政策）。适用于需求规格、概要设计、详细设计、测试文档、追溯矩阵、UML 图或阶段收口 issue 的编写、评审与修订。

## 文档权威顺序

1. `docs/开发/<模块>开发流程.md`
2. `docs/最终提交/软件需求规格说明书.md`（SRS）
3. `docs/最终提交/软件概要设计说明书.md`（HLD）
4. `docs/最终提交/软件详细设计说明书.md`（DSD）
5. `docs/过程/{需求,概要,详细设计,测试}/` 对应模块源稿
6. 涉及页面/交互时 `docs/过程/UI设计参考/`

最终提交文档定义当前需求、接口、数据、模块与验收边界；过程稿提供细节与追溯。冲突时不得静默自选新设计：指出不一致，并把改动限制在 issue 授予的权限内。

基线关系：SRS 是需求 ID 与语义的冻结基线；HLD 是子系统边界、共享抽象、接口前缀、跨模块依赖基线；DSD 实现两者。源稿是被整合的素材，与最终文档冲突时不具权威。

## 阶段所有权

| 阶段 | 模块负责人编辑 | 全局/整合者控制 |
| --- | --- | --- |
| 需求 | 本模块功能/非功能小节、用例、追溯行 | 全局范围、参与者、术语、总体结构 |
| 概要 | 本模块 2.5/2.6、页面、API、数据实体/表、场景 | 全局架构、统一接口/数据约定、聚合 |
| 详细设计 | 本模块页面/API/服务/实体/表/状态/异常/测试提交稿 | 主详细设计文档与跨模块整合（除非 issue 精确指定行） |
| 测试 | 本模块测试数据、用例、执行证据、手工检查、风险结论 | 汇总测试报告、FAT/UAT 决策、其他模块结果 |

模块负责人评审影响本模块的全局章节并协调依赖契约，但不默认改写整合者内容。

## 追溯链

保持规范链与标识符：

```text
FR-<MOD> / NFR-<MOD> -> UC-<MOD> / OP-<MOD> -> 概要模块/页面/API/数据设计
-> DSD / UI-<MOD> / API-<MOD> / SVC-<MOD> / DB-<MOD> -> TC-<MOD> / MAN-<MOD>
-> 可执行证据与演示场景
```

用 `FR-HWK`、`TC-HWK`；`FR-HW`、`TC-HW` 是旧缩写。不发明或重排 ID 让文档显得完整。

## 评审工作流（最多三轮）

1. 建立基线与清单：列出源稿文件、最终文档章节、SRS 的 `FR-*`/`NFR-*` ID 集合，做覆盖映射。
2. 第一轮：源稿整合与明显遗漏——最终文档是否无声丢掉源稿的实体、API、日志、统计快照；旧 ID 是否规范化到 SRS。
3. 第二轮：SRS 语义覆盖与设计质量——每个需求是否可追溯到设计元素；高内聚低耦合、信息隐藏；数据/接口/流程闭环；性能/可靠性/安全是否有具体设计控制而非泛泛承诺。
4. 第三轮：残余高风险一致性问题——图表、表格、术语、角色名、状态枚举、提交措辞。
5. 用户要求修复时直接修：先修 ID 漂移与语义漂移；只恢复支持 SRS 范围的源稿能力；补缺失页面/API/服务/表/状态机/流程/异常/测试/追溯行；统一接口路径与标识符；删除或降级占用冻结 ID 的未批准特性。保留文档既有语言、编号风格与 Markdown 结构。
6. 完成前验证：重新对比 ID 集合、搜旧 ID/占位/草稿措辞/空表格、跑 `git diff --check`。

## 各层检查清单

### SRS
每个 `FR`/`NFR` 有唯一 ID；可追溯到来源材料或明确的范围决策；可测试/可验证；性能与时间用可度量阈值；"待定"、"合理时间"、"按需"等模糊词已消解或显式限定；数据需求支撑功能需求；接口需求支撑跨模块流程；验收标准用 `Given/When/Then`；追溯表连接需求-用例-数据-接口-测试-交付物；图有本地资产或稳定引用、有标题、术语与正文一致；未解决的遗留问题不与冻结需求矛盾。

### HLD
需求 ID 与 SRS 完全一致（无指错语义项）；模块职责清晰、无横向业务耦合；共享能力作为基础设施或显式抽象而非业务模块互相依赖；数据归属与跨模块访问规则明确；跨模块表引用标为逻辑引用（除非有意物理约束）；接口统一 `/api/v1` 前缀且 API 表不违反；每条需求可追溯到 UI/API/实体/表/流程/测试；图有编号标题；Mermaid 图、表格、术语、角色名、状态枚举与正文一致。

### DSD
每个 SRS 需求 ID 在 DSD 中同义出现；每个功能有可实现的 UI/API/服务/数据/流程/测试覆盖；非功能需求有具体设计控制；不发明与 HLD 冲突的模块归属；API/页面/表/服务/测试 ID 在模块章节与全局矩阵一致；状态名与流转匹配 API 响应、表、流程、测试；跨模块调用用显式 client/DTO/事件/共享抽象而非直连表；相似设计元素合并而非复制；性能含分页、索引、异步、缓存/快照、资源上限、有界响应目标；可靠性含持久化点、事务边界、幂等、重试/补偿、失败态处理；安全含鉴权、授权、数据归属、隐藏数据保护、文件安全、审计日志、沙箱；无占位符、空追溯单元格、陈旧源稿措辞。

## 复用启发式（DSD）

- LAB 与 HWK 都评代码：抽取/复用 `EvaluationTask`、`Evaluator`、`SandboxExecutor`、`EvaluationResult`、资源限制与评测状态语义；只保留各自的任务提交、计分与来源成绩规则。
- 多模块需要课程权限检查：走共享 `CoursePermissionClient`，不复制权限逻辑。
- 多模块发通知：走共享事件发布器与 LRN 事件端点，不在各模块内嵌通知存储。
- 多模块管文件：用 `FileStorageService` 抽象，业务表存文件 ID 或受控元数据。
- GRD 读 LAB/HWK 成绩：用来源成绩 DTO 与同步元数据，不直依赖内部表。

## 提交措辞替换表

| 草稿措辞 | 替换为 |
| --- | --- |
| 建议、可先、必要时、后续可 | 明确设计决策或限定范围的扩展点 |
| 首版、暂定、待确认 | 实现范围或项目边界 |
| 可接受时间、合理范围 | 可度量阈值或有界行为 |
| 视情况记录 | 精确审计规则或触发条件 |
| 不实现 X，首版 Y | X 不属于本设计范围；Y 为设计通道/机制 |

## UML 与图表政策

对交付物中的每个 UML 图（用例、类、时序、活动、状态、组件、包、部署、对象图）：

- 查看相邻图表并复用其既定可编辑源格式、渲染器、静态资产类型、主题、命名与目录布局。
- 当前 OnlineJudge 文档工具链中，Mermaid `.mmd` 源放在对应的 `docs/diagrams/srs`、`arch`、`dsd` 层目录，相邻图遵循该约定时用 `scripts/dev/render-mermaid.mjs` 渲染 SVG 资产。
- 每图一个可编辑源，渲染后的静态资产提交到对应最终文档资产路径。
- 渲染并目检标签、箭头、生命线、分支守卫、裁剪与可读性；只编译不等于可读。
- 保留图号、标题、UC/OP 标识符与文档引用。
- 不为同一图引入第二可编辑源或模块专属视觉体系；不做顺手转换范围外图表。
- 不经仓库级决策不为单一模块引入另一套图表工具。

## 验证命令

```bash
# SRS 与 DSD 的 ID 集合对比（缺失/多出）
rg -o '\b(FR|NFR)-[A-Z]+-[0-9]{2}\b' docs/最终提交/软件需求规格说明书.md | sort -u > /tmp/srs_ids.txt
rg -o '\b(FR|NFR)-[A-Z]+-[0-9]{2}\b' docs/最终提交/软件详细设计说明书.md | sort -u > /tmp/dsd_ids.txt
comm -23 /tmp/srs_ids.txt /tmp/dsd_ids.txt
comm -13 /tmp/srs_ids.txt /tmp/dsd_ids.txt

# 草稿措辞与陈旧标识
rg -n '首版|建议|后续|如需|若需|可先|必要时|待补充|TODO|TBD|暂定|占位|未定|待.*确认|进一步确认|可接受' docs/最终提交/软件详细设计说明书.md
git diff --check -- docs/最终提交/软件详细设计说明书.md
```

## 测试证据规则

- 行为变更走 Red-Green-Refactor。
- 纯文档变更也要 `git diff --check`；文档声明结构性契约时补可执行的文档验证脚本。
- 图表变更必须渲染 + 目检。
- 记录确切命令、必要时的日期/环境、数量、结果与残余风险。
- 场景闭环用 `PASS`/`FAIL`/`BLOCKED`；跳过的环境性检查是披露的风险或阻塞，不是伪造的通过。
- 共享 E2E 证据归其所属 issue：引用前实际运行或核验，不拷贝结果。
