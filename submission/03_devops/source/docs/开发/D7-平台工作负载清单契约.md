# D7 平台工作负载清单契约（#306）

`deploy/platform/workloads.json` 是唯一工作负载正本。它定义 9 个 workload：gateway、identity-service、course-service、assessment-api、assessment-worker、grade-service、frontend、rabbitmq、mysql。业务服务只有 Course（CRS+LRN）、Assessment（LAB+HWK）和 Grade（GRD）；Identity 是支撑服务。

迁移 Job 固定顺序为 identity → course → assessment → grade。每个 Job 使用 `database/mysql/migrate-service.sh --schema <owner>`，必须可重复执行、阻断流量、记录 checksum；失败时停止后续 Job 和切流，回滚仅可切回记录 digest 或使用前向修复/批准恢复。

Course workload 同时包含当前 `crs/**` 与 `lrn/**` 源码输入，公开 `/api/v1/learning/**`、`/api/v1/notifications/**` 与课程 API 均路由到 Course。四个运行账号与 schema 的允许/拒绝矩阵在 `database/ownership/schema-account-matrix.csv`；任何运行账号跨 schema/DDL 均失败关闭。

```sh
python3 scripts/platform/validate_workload_manifest.py \
  --schema deploy/platform/workload-manifest.schema.json \
  --manifest deploy/platform/workloads.json
node scripts/ci/verify-three-service-baseline-306.mjs
```

当上述验证、契约正反例、Mermaid 渲染和 disposable MySQL 四账号迁移/回滚/重复执行均通过后，向下游发布：

```text
BASELINE_READY issue=#306 sha=<THREE_SERVICE_BASE_SHA> contracts=contracts/v2 manifest=deploy/platform/workloads.json evidence=<PR evidence>
```

## #318 disposable 环境、制品与回滚

`#318` 不复用 D3 的 `deploy/docker/compose.yml`。它由同一份 manifest 渲染 Compose 和 Kubernetes，避免旧 `backend` 容器、课程单库或固定密码进入最终九 workload 拓扑。

```sh
git_sha="$(git rev-parse HEAD)" # 必须是完整 40 位 SHA

# 在依赖、测试、七个 workload 镜像和 migration runner 全部成功后，生成
# plan、每个镜像的本地内容 digest、SPDX SBOM 和 artifact-manifest.json。
bash scripts/platform/build_workload_images.sh --git-sha "$git_sha"

# 生成一次性 MySQL/RabbitMQ 凭据，执行 4 个迁移，然后等待 9 个 workload。
# 默认退出时只删除本次唯一 project 的容器与 volumes，证据目录会保留。
bash scripts/platform/run_disposable_environment.sh --git-sha "$git_sha"
```

成功输出的唯一通知格式为：

```text
ENVIRONMENT_READY issue=#318 sha=<40-char-sha> endpoint=http://127.0.0.1:<port> workloads=9 migrations=4 ready=<count> evidence=<directory>
```

失败验证不是跳过门禁：`--inject-failure migration` 会在第一个 migration Job 前受控退出，`--inject-failure readiness` 会让全部 HTTP/process healthcheck 失败。两种模式都要求 Compose 本身非零退出并把 `compose ps`、按服务聚合日志、镜像 revision 写入证据目录后，才输出 `DEPLOYMENT_FAILURE_CONFIRMED`。

```sh
bash scripts/platform/run_disposable_environment.sh --git-sha "$git_sha" --inject-failure migration
bash scripts/platform/run_disposable_environment.sh --git-sha "$git_sha" --inject-failure readiness
```

渲染器不写入任何 secret 值。Compose 只保留环境变量引用，Kubernetes 只引用名为 `onlinejudge-platform-runtime` 的 Secret；其迁移 Job 运行 `onlinejudge/platform-migration-runner:<SHA>`。`platform.yaml` 是审计用库存，不得直接 `kubectl apply`，因为 Kubernetes 不会把 YAML 文档顺序解释为依赖。Kubernetes 调用方必须先把已验证的镜像推到其 registry，并按同一 SHA 创建 runtime Secret，然后执行：

共享的前端镜像仍保留单体开发期的 API 上游名 `backend:8080`。九 workload 环境不增加同名 workload，也不改变开发期镜像：渲染器从 `deploy/platform/frontend-disposable.conf.template` 生成仅用于 disposable 交付的前端代理配置。Compose 将使用 Docker DNS (`127.0.0.11`) 的配置与生成的 Compose 文件一同写入证据目录并只读挂载；Kubernetes 将使用集群 DNS (`kube-dns.kube-system.svc.cluster.local`) 的配置渲染为 `frontend-proxy-config` ConfigMap。两种配置都通过变量形式的 `gateway:8080` 在请求时解析网关，因而 frontend 可先于 gateway Ready 启动，浏览器 API 请求仍全部收敛到 gateway。

```sh
bash scripts/platform/deploy_kubernetes_disposable_environment.sh \
  --git-sha "$git_sha" \
  --namespace <disposable-namespace>
```

该入口依次执行基础设施 Ready → runtime account init → identity → course → assessment → grade migration → 业务 workload Ready → gateway 切流。任一阶段失败时脚本收集 `kubectl` 状态、事件与 Job 日志后非零退出，绝不创建后续阶段或切流。

回滚只接受已由构建命令生成的制品清单，且会逐 workload 校验清单镜像引用与历史 `workloads.json` 渲染出的规范引用完全一致，再校验本地 image ID/digest 与 SHA；它拒绝 `latest`、替换的仓库或标签：

```sh
bash scripts/platform/rollback_disposable_environment.sh \
  --from-sha <40-char-previous-sha> \
  --artifact-manifest output/issue-318/<sha>/artifacts/artifact-manifest.json \
  --env-file <runtime-secret-env-file> \
  --project-name <existing-disposable-project>
```
