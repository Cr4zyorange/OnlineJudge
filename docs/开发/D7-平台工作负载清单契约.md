## 1. 文件、执行方式与扩展规则

| 路径 | 作用 | 消费者 |
| --- | --- | --- |
| `deploy/platform/workloads.json` | 当前 10 个工作负载、5 个迁移 Job、触发图、晋级和 D3 退役条件的声明 | #318 编排、#319 观测、后续 Compose/Kubernetes 模板 |
| `deploy/platform/workload-manifest.schema.json` | JSON Schema draft 2020-12 的机器接口；字段和 Secret 边界的正本 | 编辑器、CI 和验证器 |
| `scripts/platform/validate_workload_manifest.py` | 无第三方依赖的 Schema 子集和跨字段语义校验；也计算路径影响集 | 本地、GitHub Actions、部署 Job |
| `scripts/platform/tests/test_validate_workload_manifest.py` | 正例及缺字段、重复端口、未知依赖、环依赖反例 | CI 回归测试 |

在仓库根目录执行：

```sh
python3 scripts/platform/validate_workload_manifest.py \
  --schema deploy/platform/workload-manifest.schema.json \
  --manifest deploy/platform/workloads.json

python3 -m unittest -v scripts.platform.tests.test_validate_workload_manifest
```

现有 `ci-quality-gate` 的 `contracts-gate` 会调用 `scripts/ci/contract-verify.sh`，其中按上面的**同一命令**执行 schema/语义校验和本 unittest 回归；原始命令回显和输出保存在并上传为 `ci-artifacts/contracts-gate/consumer/gate.log`。因此新 delivery 输入不是仅在 PR 描述中列出的本地检查。

新增工作负载只修改一个 `workloads[]` 声明和其必要的构建/部署模板：必须给出 `name`、`type`、`sourcePaths`、`dockerfile`（官方镜像为 `null`）、`image`、`ports`、三类健康检查、`dependsOn`、`migrationJob`、配置/密钥、资源、`pathTriggers` 和入口流量。不得复制一套 CI job。每一个 `sourcePaths` 项都必须被该 workload 的 `pathTriggers` 覆盖；每一个 migration Job 的 `sourcePaths` 都必须被其 `forWorkload` 的 `pathTriggers` 覆盖。验证器允许扩展工作负载，但拒绝遗漏触发路径、未知依赖、端口冲突、环形拓扑和缺失的 v2 核心工作负载。

每个 workload 的 `image.sbomRequired` 必须为 `true`，验证器拒绝 `false`。`image.build=true` 的镜像必须用完整 `GIT_SHA` 标记、生成 SBOM，并在制品清单记录不可变 digest。`image.build=false` 是已锁定版本的基础设施镜像；它同样必须出现在 SBOM/制品清单，不能以 `latest` 替代版本。

## 2. 五业务域与十个工作负载

五个业务服务是 **Identity、Course、Assessment、Grade、Learning**。Assessment 有两个部署单元：同步 API 和持久任务/租约/heartbeat/generation/fencing 模型的 Worker；它们不是两个业务域。`gateway`、`frontend`、RabbitMQ 和 MySQL 是基础设施/接入工作负载，不改变五服务计数。

| 名称 | 类型 | 源码/构建逻辑路径 | 镜像 | 容器端口 | 依赖与流量 |
| --- | --- | --- | --- | ---: | --- |
| `gateway` | gateway | `services/gateway/**` | `onlinejudge/gateway:${GIT_SHA}` | 8080 | 对外唯一 HTTP 入口；`traffic.browserEntry` 把浏览器 `/` 路由到 `frontend`，并路由五个 API 服务 |
| `identity-service` | service | `services/identity/**`；当前单体 `auth/**` | `onlinejudge/identity-service:${GIT_SHA}` | 8081 | 只依赖 MySQL；签发 JWT/JWKS |
| `course-service` | service | `services/course/**`；当前单体 `crs/**` | `onlinejudge/course-service:${GIT_SHA}` | 8082 | 只依赖 MySQL；本地验 JWT，不同步依赖 Identity |
| `assessment-api` | service | `services/assessment/**`；当前单体 `lab/**`、`hwk/**` | `onlinejudge/assessment-api:${GIT_SHA}` | 8083 | 只依赖 MySQL；写本地事务/outbox 后异步收敛 |
| `assessment-worker` | worker | `services/assessment/**`；当前单体 `lab/**`、`hwk/**` | `onlinejudge/assessment-worker:${GIT_SHA}` | — | MySQL + RabbitMQ；处理评测租约和队列，不接收 HTTP 流量 |
| `grade-service` | service | `services/grade/**`；当前单体 `grd/**` | `onlinejudge/grade-service:${GIT_SHA}` | 8084 | 只依赖 MySQL；消费最终一致性事件但 API 不因 broker 短故障摘流 |
| `learning-service` | service | `services/learning/**`；当前单体 `lrn/**` | `onlinejudge/learning-service:${GIT_SHA}` | 8085 | 只依赖 MySQL；通知/投影由可靠消息最终收敛 |
| `frontend` | frontend | `frontend/**` | `onlinejudge/frontend:${GIT_SHA}` | 80 | 只可由 `gateway -> frontend` 浏览器入口访问；SPA API 请求只到 gateway，不直连业务服务 |

| `mysql` | database | `database/**`、`deploy/mysql/**` | `mysql:8.4` | 3306 | 五 schema 可共用一个物理实例；**这是课程环境物理单点，不是 HA 声明** |

现有单体目录仍是 v2 拆分前的逻辑映射输入。#336 不创建 `services/**`、RabbitMQ topology、五 schema 迁移或网关路由实现；这些由 #317、#318、#341 和相应服务 Issue 以同一个 manifest 消费。不得为了让本 Issue 的文档“看起来可运行”而伪造服务 Dockerfile 或把单体 `backend` 宣称为五服务。

## 3. 健康检查与故障域

每个工作负载都有 `startup`、`liveness`、`readiness` 三类声明。`liveness` 只判断进程/事件循环还活着；`startup` 允许启动期等待职责所必需的本地依赖；`readiness` 只判断该工作负载**当前职责必需**的依赖，绝不把“所有下游都正常”写成 Ready 条件。

| 工作负载 | startup/readiness | liveness | 故障语义 |
| --- | --- | --- | --- |
| API 服务 | 本服务 MySQL schema/账号可用 | HTTP liveness | RabbitMQ、Learning、Grade 或其他下游的短时故障不让已能写本地事务/outbox 的 API 级联摘流 |
| `assessment-worker` | MySQL 租约存储 + RabbitMQ consumer 可用 | Worker event loop | broker 故障让 Worker Not Ready、形成可观测积压；不使 Assessment API 重启或摘流 |
| `gateway` | 路由配置已加载 | 网关进程 | 下游部分故障由路由返回受控 5xx/降级；网关 readiness 不探测每个下游 |
| `frontend` | `/` 静态内容可服务 | `/` | API 下游故障不使静态页被摘除 |
| RabbitMQ/MySQL | 官方命令探针 | 官方命令探针 | 作为基础设施分别报告；不将其健康伪装为业务服务 HA |

业务 API 不信任 gateway 透传的身份头作为唯一安全边界：它们按 #338 的 JWT/JWKS 或工作负载身份约定本地验证。gateway 的职责是剥离客户端伪造头、路由和透传；Identity 不成为每次请求的同步依赖。

## 4. 配置和密钥边界

manifest 只保存配置键名和 Secret 元数据，**没有也不得加入值**。每个 Secret 都要求 `redact=true` 与 `imageBuild=forbidden`：不能进入 Docker build context、镜像层、SBOM 内容、日志、诊断归档或 `kubectl describe` 输出。

| 类别 | 规范键/边界 |
| --- | --- |
| JWT/JWKS | `IDENTITY_JWT_SIGNING_KEY` 仅 Identity 运行时注入；其他服务使用非敏感的 issuer/audience/JWKS URI 配置和信任材料，绝不复制签名私钥 |
| 服务身份 | `*_SERVICE_IDENTITY` / `*_WORKER_IDENTITY` 为按工作负载、按受众的短时身份或 mTLS 工作负载身份；禁止全局 `X-Internal-Token` |
| RabbitMQ | `RABBITMQ_PASSWORD` 是运行时 Secret；host/port/vhost/user 是非敏感配置；拓扑初始化与应用凭据最小化授权由 #317/#318 实现 |
| 五数据库账号 | `IDENTITY_DATABASE_PASSWORD`、`COURSE_DATABASE_PASSWORD`、`ASSESSMENT_DATABASE_PASSWORD`、`GRADE_DATABASE_PASSWORD`、`LEARNING_DATABASE_PASSWORD` 分开注入；每个服务只得到自己的 schema 账号 |
| MySQL 管理 | `MYSQL_ROOT_PASSWORD` 只给初始化、数据库运维/迁移控制面；不注入业务服务 |

`MYSQL_PHYSICAL_INSTANCE_MODE` 必须在 DEV/FAT/UAT/PRO 明示该实例是课程环境的共享物理实例。它不授予跨 schema SQL、跨库 join、共享 repository 或共享数据库账号；这些均由 #309 的最终 ownership/账号矩阵约束。

## 5. 五 schema 迁移、部署与回滚

`migrationJobs[]` 是唯一的顺序。当前 v2 顺序固定为：

```text
MySQL Ready
  -> identity-migrations
  -> course-migrations
  -> assessment-migrations
  -> grade-migrations
  -> learning-migrations
  -> API/Worker rollout and readiness
  -> gateway traffic switch
```

每个 Job 是一次性、可安全重跑、`blocksTraffic=true`、`failurePolicy=block` 的 Job。任何一个 Job 失败都必须：保留原始 stdout/stderr、非零退出、停止后续 Job 与新应用切流，并把失败版本/digest/环境记录入证据；不得删除持久卷或跳过失败 Job 继续部署。

MySQL DDL 不能承诺全文件原子回滚。回滚策略是先确认新 schema 与旧镜像的兼容窗口，再把 gateway 流量切回已记录 digest；若迁移不兼容，以新增的前向修复迁移或经审批的备份恢复处理。绝不原地修改已经登记的迁移、也不把“删除数据库卷”称作回滚。#341 负责实际五 schema 迁移和可演练数据恢复；#336 只冻结其编排约束。

## 6. 确定性 path-to-workload 构建图

命令可重复计算路径影响集：

```sh
python3 scripts/platform/validate_workload_manifest.py \
  --schema deploy/platform/workload-manifest.schema.json \
  --manifest deploy/platform/workloads.json \
  --changed-path services/assessment/src/main/java/App.java \
  --changed-path frontend/src/App.vue
```

结果会直接列出 `assessment-api`、`assessment-worker`、`frontend`。单一路径只构建其匹配工作负载；Assessment 的共享源码自然同时影响 API/Worker。`sharedTriggerPaths`（manifest/schema/validator、D7 文档，以及由 #305/#309/#338 合入的任何 `docs/开发/D6-*.md` 正式契约）改变时，必须构建所有自建工作负载：gateway、五业务部署单元、Worker 和 frontend。这样在上游尚未合入时不会猜测其最终文件名。RabbitMQ/MySQL 没有仓库自建镜像，仍需记录版本与 SBOM，但不因共享契约变更重建。

`sourcePaths` 不是说明性字段：验证器以 glob 包含关系机械检查其到 `pathTriggers` 的覆盖，并强制当前仓库仍存在的单体输入。映射固定为 `auth/** -> identity-service`、`crs/** -> course-service`、`lab/** + hwk/** -> assessment-api + assessment-worker`、`grd/** -> grade-service`、`lrn/** -> learning-service`；不能以不存在的 `course/**`、`homework/**`、`grade/**`、`learning/**` 或 `evaluation/**` 代替。`backend/src/main/java/com/onlinejudge/common/**`、`backend/src/main/java/com/onlinejudge/integration/**`、`backend/src/main/resources/**` 与 `backend/pom.xml` 是共享编译/运行输入，任一变更必须同时选择全部六个后端应用 workload（Identity、Course、Assessment API/Worker、Grade、Learning）。缺少任一个 source/trigger 声明时 validation 必须失败，而不能静默返回空的 affected set。五个 migration Job 也以同样方式绑定到其 owning workload。这条约束让消费者可把 `affectedWorkloads` 直接用作构建/测试矩阵输入。

该集合是构建/测试矩阵输入；运行依赖图是部署顺序输入，两者不得混淆。#318 可在此矩阵上添加跨服务集成测试扩展集，但不能把未匹配的服务静默加入或遗漏。

## 7. 制品、环境晋级与证据

环境顺序固定为 `DEV -> FAT -> UAT -> PRO`。晋级的是同一 Git SHA、同一 image digest 和同一迁移/配置契约，不是跨环境重新以 `latest` 构建。每次部署至少归档：

- base/head Git SHA、每个工作负载 image tag + digest、OCI revision；
- 每个自建镜像的 SBOM、制品清单及其 checksum；
- manifest schema/语义校验和 path-resolution 的原始输出；
- 5 个迁移 Job 的顺序、退出码、输出以及是否发生失败；
- startup/liveness/readiness 的原始探针结果；
- 该环境回滚演练所用的旧 digest、兼容性判断、切流命令和结果。

Secret 值、JWT、数据库 DSN 中的密码、RabbitMQ URI 密码、用户提交正文和评测文件内容都不属于可归档证据。记录键名、工作负载名、版本和遮蔽后的诊断即可。

## 8. 交付顺序

1. 校验 manifest，计算变更工作负载；校验失败即停止。
2. 为目标环境创建 ConfigMap/Secret 引用，验证没有 Secret 值进入构建日志或渲染产物。
3. 启动 MySQL、RabbitMQ；等待各自健康。
4. 按第 5 节运行五个 migration Job；任一失败即停止。
5. 按无环 `dependsOn` 拓扑启动自建工作负载，等待相应 startup/readiness；`frontend` Ready 后 `gateway` 才能部署其 `/ -> frontend` 浏览器入口。
6. 验证 API 本地事务/outbox 在 broker 或非关键下游短故障时仍保持 Ready；验证 Worker 的 broker 故障显示为积压/Not Ready 而不是 API 级联下线。
7. gateway 只在上述条件满足后切换路由；执行浏览器主流程和可观测性验收。

## 9. D3 兼容窗口与退役

`docs/开发/D3-CICD-共享契约.md` 仍是现存单体 `mysql/backend/frontend` 的 D3 历史正本，不被本 Issue 重写。v2 使用 `d3Retirement.compatibilityWindow = v2-parallel-until-gates-pass`，含义是：D3 在 v2 真实环境未验收前可保留作旧闭环基线，但不可继续成为新的五服务交付输入，也不可通过把 v2 名称映射回 `backend/frontend` 来伪造通过。

退役顺序如下：

1. #336 合入 schema、manifest 和验证器；#318/#319 可依据草案开发通用模板/观测配置。
2. #317/#341/服务 Issue 提供真实 RabbitMQ、五 schema、路由和镜像元数据；#318 在 disposable 环境运行十个声明工作负载。
3. 同一环境完成迁移失败阻断、逐服务 digest 回滚、API/Worker/消息积压故障验收后，停止 D3 `backend/frontend` 专用构建变量和三服务部署消费者。
4. 只有第 10 节所有门通过，才另开变更删除 D3 流水线、Compose/Kind 的旧专用实现；#336 本身不删除仍被现有 D3 回归使用的文件。
