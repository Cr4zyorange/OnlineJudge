## 2. 身份、网关和服务身份

### 2.1 用户令牌与离线验签

用户访问令牌是 Identity 用非对称密钥签发的短时 JWT，claims、JWKS response 和 token mint API 都由 `identity.openapi.json` 机器冻结。服务只接受配置的签名算法及带 `kid` 的 token，验证 `iss=onlinejudge.identity.v2`、`aud=onlinejudge.api`、时钟偏差、`iat`、`exp` 与必填身份/权限 claims。JWT 绝不写入日志、错误响应或事件。

业务服务缓存 JWKS 到安全 TTL；密钥轮换必须保留旧 `kid` 至少覆盖最大 token lifetime 和 cache overlap。Identity/JWKS 暂时不可用时，缓存的有效 key 继续离线验签未过期 token；未知 key 只做一次限流刷新，刷新仍失败按 401 或 503 的标准 Error 返回，绝不放行。

`securityVersion` 在会话撤销、密码/角色/权限/账号状态变化时递增。可靠事件让每个服务更新本地最小版本；token lifetime 限制事件延迟窗口。对权限的课程范围判断仍只由 Course 给出，不能把全局 permissions 当作课程成员授权。

### 2.2 Gateway 责任边界

Gateway 仅：

- 剥离客户端给出的内部身份和 `X-User-*` 头；
- 生成或校验格式正确的 `X-Request-Id`，并跨 HTTP/消息传递 correlationId；
- 路由、TLS 终止、大小限制和透传客户端 `Authorization`。

业务服务始终自己验证 user JWT 与服务身份；它们不把 gateway、来源 IP 或客户端传来的用户 ID 视为安全事实。Gateway 不做 session introspection 的唯一判断，也不注入可被业务服务盲信的用户 Header。

### 2.3 内部服务身份

调用方选择下列之一：

1. `X-OnlineJudge-Service-Authorization` 携带 Identity 签发的短时 service JWT，`aud` 严格等于目标服务，`sub` 为发起 workload，scope 为 endpoint 所需最小权能；接收方本地验签。
2. workload mTLS 身份经部署环境映射为等价的 service、audience 和 scopes；接收方验证证书链、SPIFFE/工作负载名及授权映射。

二者没有降级顺序：若请求要求服务身份，任一种**独立有效且有 scope**的机制都可通过。缺失、格式错误、验签失败、过期或 `aud` 不匹配的 service JWT（或无效/过期的 mTLS workload identity）在没有另一种独立有效身份时一律是 `401 SERVICE_IDENTITY_INVALID`；已经认证但不具 endpoint 所需 scope 的主体一律是 `403 SERVICE_IDENTITY_FORBIDDEN`。禁止全局共享 `X-Internal-Token`、硬编码静态 secret、进程内 SPI 和跨服务 Repository/SQL。用户发起的内部链路同时携带 user JWT，以便最终服务自行鉴别用户；纯异步 worker 使用 service identity 和事件事实，不伪造用户 token。

## 3. 同步 API 共同规则

| 项 | v2 规则 |
| --- | --- |
| 路径和版本 | 内部路径为 `/internal/v2/**`；公开 `/api/v1/**` 在迁移期保持其业务含义，不能以内部路由泄漏给浏览器。 |
| Request ID | 每个操作要求 `X-Request-Id`；下游 HTTP 和 EventEnvelope 的 `correlationId` 原样继承。 |
| 写幂等 | 所有内部 `POST`/命令要求 `Idempotency-Key`（16–128 chars）。同 key + 同语义请求返回原结果；同 key + 不同请求返回 409 `IDEMPOTENCY_KEY_REUSED`。 |
| 分页 | 列表使用 `page`（0 起）和 `size`（1–100），返回 `items/page/size/total`；不得把无限列表作为内部默认。 |
| 错误 | 标准 Error 含 `code`、安全 message、`requestId`、`retryable`。对服务身份，401 固定为 `SERVICE_IDENTITY_INVALID`（缺失/无效/过期/wrong-audience），403 固定为 `SERVICE_IDENTITY_FORBIDDEN`（已认证但 scope 不足）；用户 token 的 401/403 也遵循认证先于授权。404 是调用可见的资源不存在，409 是幂等冲突，503 是受控依赖不可用。 |
| 超时和重试 | 每个 operation 声明总 timeout；调用端一次有界调用，GET 可在截止前做一次带 jitter 的重试，写命令只用同一幂等键重试。401/403/409/422 不重试。 |

Course 授权下游不可用时，Assessment/Grade/Learning 返回 `COURSE_AUTHORIZATION_UNAVAILABLE`（503）并不写本地业务事实。Assessment 来源成绩不可用时，Grade 原子中止本次同步、保留先前投影；不能直接查询 Assessment schema。Learning 的正常通知只消费事件，`grade.openapi.json` 与 reconciliation API 是发现 DLQ/版本缺口后的受控恢复路径，不能变成发布成功的同步前置条件。

## 4. 统一事件和失败语义

`EventEnvelope` required fields 是：`eventId`、`eventType`、`payloadVersion`、`aggregateType`、`aggregateId`、`aggregateVersion`、`occurredAt`、`correlationId`、`payload`。v2 payloadVersion 固定为 `2`；消息类型名以 `.v2` 结束。eventId 是 inbox 去重键；同一 aggregate 的 `aggregateVersion` 必须严格递增，但 broker 不保证跨聚合顺序。每个消息不只是引用通用 envelope：它还绑定 eventType 常量、aggregateType、由 payload 字段生成的 aggregateId 模板，以及 closed、required 的独立 payload schema；`x-onlinejudge-ordering` 固定为该 aggregate 的 `aggregateVersion`。

| 事件 | aggregateType / aggregateId | 闭合 payload 的必填事实 |
| --- | --- | --- |
| `identity.security-version.changed.v2` | `identity-user` / `userId` | `userId`、`securityVersion`、`changeReason` |
| `course.member.changed.v2` | `course-member` / `courseId:userId` | `courseId`、`userId`、`membershipStatus`、`memberVersion` |
| `course.announcement.published.v2` | `course-announcement` / `announcementId` | `courseId`、`announcementId`、`publishedAt` |
| `assessment.source-grade.changed.v2` | `assessment-source-grade` / `sourceType:sourceId:studentId` | `courseId`、`sourceType`、`sourceId`、`studentId`、`score`、`fullScore`、`sourceVersion` |
| `assessment.evaluation.completed.v2` | `assessment-submission` / `submissionId` | `courseId`、`submissionId`、`evaluationStatus`、`evaluationVersion`、`completedAt` |
| `assessment.homework.published.v2` | `assessment-homework` / `homeworkId` | `courseId`、`homeworkId`、`title`（1–100 字符）、RFC3339 `deadline`、`receiverScope=COURSE_ACTIVE_STUDENTS`、`publishedAt`；禁止 roster |
| `grade.published.v2` | `grade-publication` / `publicationId` | `courseId`、`publicationId`、`publishedAt`、`publicationVersion` |
| `grade.review.processed.v2` | `grade-review` / `reviewRequestId` | `courseId`、`reviewRequestId`、`studentId`、`reviewStatus`、`resultVersion`、`processedAt` |

| 发生的情况 | 生产者 | 消费者 |
| --- | --- | --- |
| API-HWK-03 本地 Homework + outbox 事务成功 | Homework 立即为 `PUBLISHED` 且学生可见；Learning/broker 不可用不得回滚 | Learning 以 at-least-once 消费事件，依靠自己的 Course 成员投影按 `receiverScope` 创建任务/通知 |
| API-HWK-03 本地 Homework + outbox 事务失败 | 不提交 `PUBLISHED` 或 outbox，返回 `503/HWK_5003` 并保持 `DRAFT`；这不是下游通知失败 | 不适用 |
| 事实写入成功但 broker 暂不可用 | 提交本服务事实和 outbox；#337 负责有限重试，绝不因 Learning/Grade 不可用回滚事实 | 不适用 |
| 重复投递 | 可再次发送同 eventId | 在本地事务中判重，成功 no-op |
| 乱序旧版本 | 正常投递 | 忽略早于或等于已投影版本的事实 |
| 版本缺口 | 正常投递 | 持久化 gap，暂停该 aggregate 的破坏性更新，创建 reconciliation 请求并告警 |
| 耗尽可重试错误 | outbox 留诊断，由运维重放 | 进入 DLQ，保存 envelope、错误、重试次数、correlationId；修复后受控 replay |
| payload/权限不可恢复错误 | 不产生不合规 event | 直接 DLQ，不进行无限重试 |

这是 at-least-once + 幂等；对 `assessment.homework.published.v2`，Learning 只使用 payload 中有界的标题、截止时间和 `COURSE_ACTIVE_STUDENTS` scope，不回读 Assessment 详情，也不接受事件携带的 `recipientUserIds`/学生 roster。任何“exactly-once”、“内存 best-effort 就足够”或“稍后重试”但未定义所有者、上限和恢复方式的说法都不是 v2 契约。

## 5. 兼容和 v1 迁移

新增可选字段只在相同 `payloadVersion` 的容忍期内允许；新增必填字段、字段含义改变、删除字段、修改枚举语义或改变授权/失败语义，必须新增事件类型或递增 payloadVersion，并让生产者/消费者在 CI 单独校验。消费者忽略未知可选字段；不知道的 major payloadVersion 进入 DLQ，不猜测解释。

| v1 (#310) | v2 (#338) |
| --- | --- |
| AUTH/CRS 基础服务 + 评测 + 成绩 + 学习通知四服务 | Identity、Course、Assessment、Grade、Learning 五服务 |
| `HeaderCurrentUserProvider`/网关注入 `X-User-*` | user JWT 本地验签，Gateway 只清洗和路由 |
| 全局 `X-Internal-Token` | target-audience JWT 或 mTLS workload identity |
| `CoursePermissionClient`、`SourceGradeClient` 进程内 SPI | versioned authenticated `/internal/v2/**` OpenAPI |
| 同步 callback 与通知内存队列 | transactional outbox/inbox、at-least-once、DLQ、replay/reconciliation |
| `publishRequired` 同步通知成功才发布、下游失败返回 `503/HWK_5003` | **明确语义变更：** API-HWK-03 的 Homework + outbox 本地事务成功即 `PUBLISHED`；仅本地事务失败返回 `503/HWK_5003`/`DRAFT`；Learning/broker 不可用不回滚 |

v1 代码在服务拆分前可继续运行，但所有新服务/adapter 必须先证明使用本 v2 制品。不得为“兼容”把 v1 的同步 callback、SPI、共享 repository 或 global header secret 重新引入 v2 主路径。

## 6. 可执行验证和下游使用

```bash
node scripts/ci/verify-microservice-contract-v2.mjs
git diff --check
```

脚本仅依赖 Node 标准库，验证五个 OpenAPI 3.1 文档（每个 service-identity operation 的 401/403 区分）、八个 AsyncAPI 3.0 消息、统一事件信封、v1 历史标记，以及 2 个正例和至少 2 个不兼容反例。它还以受控 mutation 证明删除 `x-onlinejudge-ordering`、清空 payload、篡改 aggregateType，以及删除作业任务的 `title`/`deadline`/`receiverScope` 都会被拒绝。下游服务先复制 `contracts/v2/examples/` 做 RED fixture；具体 outbox/inbox、RabbitMQ、schema 归属和 workload manifests 分别归 #337、#309、#336。
