# GitHub 协作与评审规范

> 适用范围：软件工程基础实践小学期项目全体成员。GitHub 是工程任务、代码变更、验证结果和评审结论的唯一可追溯正本；Notion 管理时间线与项目结论，微信群承担日常低摩擦沟通。

## 1. 工具边界

| 工具 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 微信群 | 站会、个人日报、即时阻塞和临时协调 | 长期归档、代码评审结论 |
| Notion | 每日计划、小组日报、决策、风险和阶段总结 | 代替 Issue、PR、提交与测试证据 |
| GitHub | Project、Issue、分支、提交、PR、自动评审和工程证据 | 代替每日口头同步 |

完整链路固定为：

```text
Notion 当日任务
-> GitHub Issue
-> 工作分支
-> 测试或可执行验收用例
-> Commit
-> Pull Request
-> Codex/Copilot 辅助评审
-> 项目负责人终审
-> 合并到 dev
-> 回填 Project 与 Notion 证据
```

## 2. Issue 与 Project

1. 开始工作前先确认已有 Issue；没有 Issue 时先创建，禁止用无编号分支长期开发。
2. 一个 Issue 对应一个可以独立验收的目标，至少写清：目标、范围、完成标准、依赖或风险、预期证据。
3. 一个 Issue 原则上对应一个 PR。发现范围过大时拆分 Issue，并用父子 Issue 或依赖关系串联。
4. 开始开发时将 Project 状态改为 `In progress`；PR 合并且 Issue 验收后改为 `Done`。
5. 当天无法完成时，在 Issue 或 PR 中写明已完成部分、阻塞原因和下一动作，不能只在微信群口头说明。

## 3. 分支与同步

开发集成分支为 `dev`，不要另建 `develop`。常规功能不得直接提交到 `dev`、`main` 或 `release/*`。

| 类型 | 命名 | 用途 |
| --- | --- | --- |
| 功能 | `feature/<issue-id>-<name>` | 单个 Issue 的功能开发 |
| 修复 | `fix/<issue-id>-<name>` | 开发期缺陷修复 |
| 文档 | `docs/<issue-id>-<name>` | 纯文档与协作规范 |
| 测试 | `test/<name>` | 集中功能验收 |
| 发布 | `release/<version>` | 版本冻结与发布前修复 |
| 热修复 | `hotfix/<issue-id>-<name>` | 从 `main` 发起的线上紧急修复 |

开始常规任务：

```bash
git status --short --branch
git fetch origin
git switch dev
git pull --ff-only origin dev
git switch -c feature/<issue-id>-<short-name>
```

工作区存在其他人的未提交内容时不得覆盖、回滚或顺手格式化；先绕开，确实无法绕开再在 Issue 中说明。

## 4. 开发与提交

除纯文档、纯配置和一次性脚手架外，功能、修复和重构按 `RED -> GREEN -> REFACTOR` 推进：

1. 先写失败测试或可重复验收用例，并确认它按预期失败。
2. 写最小实现使其通过。
3. 在测试保持通过的前提下整理结构，再运行相关测试。

提交信息统一为：

```text
type(scope): message
```

常用 `type`：`feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`。

每个 Commit 只处理同一类问题，不混入无关格式化、调试输出、生成物、本地配置或敏感信息。提交前至少确认：

- 改动范围与 Issue 一致；
- 相关测试、构建或验收命令已经执行；
- `git diff --check` 通过；
- 不含 Token、密码、真实环境变量和个人数据。

## 5. Pull Request

PR 目标分支统一为 `dev`，描述至少包含：

```markdown
## 目标

## 改动

## 验证

## 风险与边界

## AI 使用说明

Closes #<issue-id>
```

PR 必须满足：

- 一个 PR 只关闭一个主要 Issue，必要的子 Issue 在描述中列明；
- 变更完整、可运行、可验证，不提交孤立页面、假接口或无法联调的半成品；
- 代码、类型、数据库、测试和相关文档保持一致；
- 测试日志、截图或验收命令能够证明完成标准；
- 公共接口、数据库结构、状态枚举和跨模块 DTO 的变化必须显式说明影响范围。

## 6. 自动评审

仓库已接入 Codex 自动评审，并可能同时收到 GitHub Copilot 的建议。打开非草稿 PR、将草稿转为 Ready 或继续推送后，自动评审会按仓库配置运行；需要重新检查时，可在 PR 评论：

```text
@codex review
```

Codex 发现具体问题时会提交 Review 建议；没有建议时通常以 `+1` 反应表示完成检查。处理方式固定为：

1. 逐条判断建议是否成立，不因来源是 AI 就直接接受或忽略。
2. 成立的小问题直接修复并回复；涉及设计边界的建议先对照正式文档。
3. 推送修复后重新触发或等待下一轮检查。
4. PR 描述中的验证结果必须来自真实执行，AI 不得代写不存在的日志或结论。

自动评审只是辅助证据，不是合并授权。截至 2026-08-24，仓库尚未建立 `.github/workflows/` 下的 CI 检查；在后续 CI/CD 任务完成前，PR 必须明确记录本地验证命令和结果。

## 7. 人工终审与返工

取消组员交叉评审，所有 PR 统一由项目负责人终审。各领域负责人只负责制定本领域标准、维护模板并汇总六人的同类成果，不承担其他成员 PR 的审批责任。

项目负责人按以下顺序检查：

1. Issue 范围和完成标准是否满足；
2. 主流程、权限、异常和空状态是否闭环；
3. 公共契约、设计文档和实现是否一致；
4. 测试、构建、截图或日志是否能重复验证；
5. 是否存在安全、隐私、部署或数据迁移风险；
6. README、正式文档和提交物索引是否需要同步。

处理边界：

- **小问题由项目负责人直接调整**：通常不超过 30 分钟，且不改变需求、接口、数据库、权限、架构或主要交互。
- **大问题打回原作者修改**：涉及主流程错误、设计偏离、公共契约变化、测试缺失、明显返工或无法在短时间内安全修正。
- 返工意见必须写在 PR 中，说明问题、证据、完成标准和复查方式，不只在微信群口头通知。

## 8. 合并与收口

只有项目负责人可以作出最终合并决定。合并前确认：

- PR 不再是 Draft，自动评审已返回或已说明未返回的原因；
- 人工终审完成，所有阻断意见已解决；
- 目标分支为 `dev`，关联 Issue 可由 `Closes #...` 自动关闭；
- 当前验证仍然有效，分支没有混入无关改动；
- 需要同步的 Notion 任务、日报或决策已补证据链接。

合并后删除已完成的远端工作分支，将 Project 项改为 `Done`，并在当日小组日报中记录 Issue、PR、提交或测试链接。`monolith-start` 等关键架构切换只能在教师或助教确认后执行，不能因代码已准备好就自行启用。

## 9. 快速检查表

### 成员提交前

- [ ] Issue、分支和 PR 一一对应。
- [ ] 测试或验收用例先失败、后通过，例外已说明。
- [ ] 已运行相关验证和 `git diff --check`。
- [ ] PR 描述包含验证、风险、AI 使用说明和 `Closes #...`。
- [ ] 没有无关文件、调试内容或敏感信息。

### 项目负责人合并前

- [ ] Codex/Copilot 建议已判断并处理。
- [ ] 主流程、权限、异常、文档和证据已终审。
- [ ] 大问题已由原作者返工，小问题修改未越过设计边界。
- [ ] PR 合并到 `dev`，Issue 与 Project 状态正确。
- [ ] 当日 Notion 小组日报已记录可追溯证据。
