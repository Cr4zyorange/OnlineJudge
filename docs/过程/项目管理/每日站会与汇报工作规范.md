# 每日站会与汇报工作规范

> 目标：用最短的同步时间暴露进度、阻塞和返工，同时形成可追溯的小组执行证据。微信群负责六人原始输入，Notion 保存核实后的小组日报，GitHub 提供工程证据。

## 1. 每日节奏

| 时间 | 动作 | 负责人 | 产物 |
| --- | --- | --- | --- |
| 09:00 | 每日站会，控制在 5 分钟内 | 全员，项目负责人主持 | 当日目标与阻塞清单 |
| 11:20 前 | 个人日报发微信群 | 每位成员 | 几句话、约 200 字的真实进展 |
| 12:00 前 | 汇总小组日报到 Notion | 项目负责人 | 核实后的六人日报与小组结论 |
| 收工前 | 更新 GitHub Project 并补证据 | 各任务负责人，项目负责人复核 | Issue、PR、测试、文档或截图链接 |

若教学安排与固定时间冲突，由项目负责人最迟在前一晚于微信群统一调整；当天仍需完成同样四个环节。

## 2. 站会形式

六人依次发言，每人约 30–45 秒，只回答三个问题：

1. 昨天完成了什么，结果是什么？
2. 今天准备交付什么，完成标准是什么？
3. 当前有什么阻塞，需要谁在什么时间前协助？

站会上不展开设计争论、不现场调试、不逐行讲代码。超过 30 秒仍讲不清的问题进入“会后处理清单”，站会结束后只留下相关成员继续处理，并在 Issue 或 Notion 中记录结论。

项目负责人只负责控时、确认目标和指派阻塞处理人，不在站会上替成员编造完成情况。缺席者应在会前提交同格式文字；无故缺席和未交日报进入当天小组日报。

## 3. 个人日报标准

个人日报允许简短，但四项信息必须齐全：

```text
【姓名｜日期】
昨日/已完成：完成了什么，实际结果是什么。
今日：准备交付什么，完成标准是什么。
阻塞：无；或写明问题、影响、需要谁在何时前处理。
证据：Issue / PR / commit / 测试 / 文档 / 截图链接。
```

合格示例：

```text
【成员 A｜08-25】
已完成：补齐登录失败与会话过期两条接口测试，均已通过。
今日：修复前端会话过期提示并提交 PR，以类型检查、组件测试和登录主流程通过为准。
阻塞：无。
证据：Issue #xx，PR #xx，测试命令与结果见 PR 描述。
```

不合格表达包括“差不多了”“还在看”“完成 80%”“应该没问题”。改写为已经产生的结果、剩余事项和可验证证据；没有证据时只能写“进行中”，不能写“完成”。

## 4. 小组日报标准

项目负责人收齐六人原始日报后，可使用 GPT 压缩表达，但必须逐项核对人、任务、状态和链接。Notion 小组日报使用以下结构：

## 5. 状态与证据口径

日报只使用以下状态：

| 状态 | 含义 |
| --- | --- |
| 已完成 | 已满足完成标准，并有链接、命令结果、截图或文档等证据 |
| 进行中 | 已开始但尚未满足完成标准，必须写清剩余事项 |
| 阻塞 | 无法继续，必须写清原因、影响、处理人和期望时间 |
| 风险 | 当前可以继续，但可能影响后续时间、质量或协作边界 |
| 返工 | 项目负责人终审未通过，需原作者按明确标准修改 |

证据优先级为：可重复执行的测试或验收结果、PR 与 Commit、Issue 记录、正式文档、带时间与上下文的截图。截图不能代替可以直接提供的链接，单独一句“已完成”不构成证据。

每条关键证据应能回答：谁在什么时候，针对哪个任务，做了什么，按什么标准判定完成。

## 6. 六人分工与评审边界

- 每个人都应在小学期内轮转体验需求、设计、开发、测试、部署、文档和汇报，不把某类工作永久固定给某个人。
- 各领域负责人负责制定标准、维护模板、检查格式并汇总六人的同类产物，不等于独占该领域的实际工作。
- 取消组员交叉评审。所有 PR 由项目负责人统一终审，各领域负责人不承担 PR 审批责任。
- 项目负责人以审查、整合和修订为主：小问题直接调整，大问题写明证据与完成标准后打回原作者返工，尽量不接管成员的主体开发任务。
- 项目负责人直接调整的小问题通常不超过 30 分钟，且不得改变需求、接口、数据库、权限、架构或主流程；超过边界即按返工处理。

## 7. GPT 汇总规则

可直接使用以下提示词生成初稿：

```text
请根据下面六人的原始日报生成一份小组日报。
只整理和压缩已提供事实，不新增完成项，不推测测试结果，不改动链接、人员和任务归属。
按“出勤与站会、六人状态、小组结论、技能轮转、证据”五部分输出。
将缺少证据、完成标准不清或存在矛盾的内容列入“待核实”，不要自动补全。
```

项目负责人保存到 Notion 前必须：

1. 对照微信群原文确认六人均已覆盖；
2. 打开关键 Issue、PR 或文档链接确认可访问；
3. 把计划与完成严格分开；
4. 将不确定内容标为“待核实”，不得用流畅文字掩盖信息缺口。

## 8. 保存与归档

- 微信群保存原始输入，便于当天快速追问，但不作为最终项目管理正本。
- Notion 保存核实后的小组日报、风险、决定和每日证据索引。
- GitHub 保存 Issue、PR、Commit、自动评审、人工终审和测试证据。
- 开发期不在仓库每天复制日报；版本冻结时再按 `submission/05_management/` 的映射导出 Notion 日报、GitHub Project 快照和必要证据。
- 禁止在微信群、Notion、PR 或截图中出现密码、Token、真实环境变量、个人隐私和敏感部署信息。

GitHub 操作与评审细则见 [GitHub 协作与评审规范](GitHub协作与评审规范.md)。

## 9. 每日检查表

### 每位成员

- [ ] 参加 09:00 站会或提前补报。
- [ ] 11:20 前在微信群提交四项齐全的个人日报。
- [ ] “已完成”均有真实证据，“进行中”写明剩余事项。
- [ ] 阻塞写明影响、处理人和期望时间。
- [ ] 收工前更新本人负责的 Issue、PR 和 Project 状态。

### 项目负责人

- [ ] 站会不超过 5 分钟，问题进入会后处理清单。
- [ ] 六人日报已收齐，链接和状态已核实。
- [ ] 12:00 前将小组日报保存到 Notion。
- [ ] PR 评审队列、返工、风险和技能轮转已记录。
- [ ] 收工前补齐 GitHub Project 快照与证据索引。
