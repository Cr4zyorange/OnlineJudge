## 1 引言

### 1.1 编写目的

本《软件概要设计说明书》是"在线教学与实训平台"项目进入详细设计阶段前的重要技术文档，其编写目的如下：

**第一，明确系统总体设计方向。** 本文档从系统全局视角出发，对平台进行模块划分、架构设计、接口设计和数据结构设计，为后续详细设计阶段提供清晰的设计蓝图和技术约束。各模块负责人和开发人员可据此开展各自模块的类设计、数据库表细化、接口协议定义等详细设计工作。

**第二，统一团队设计共识。** 本文档作为项目组的整体协作底稿，将六个功能模块（AUTH、CRS、LRN、LAB、HWK、GRD）的设计方案整合到统一的文档框架中，明确各模块的职责边界、数据交互关系和接口契约，避免模块间设计冲突和重复开发。

**第三，为测试和评审提供依据。** 本文档中的功能需求设计、接口定义、数据结构设计和运行设计等内容，可作为测试负责人编写测试计划、设计测试用例的依据，也可作为项目评审阶段的重要参考材料。

**本文档的预期读者包括：** 概要设计负责人、各模块负责人、前端总设计师、后端总设计师、测试负责人以及全体开发人员。所有读者应在阅读本文档前已熟悉《软件需求规格说明书》（SRS）的内容。

### 1.2 背景

**待开发系统名称：** 在线教学与实训平台

**项目背景：** 当前高校课程教学中的理论教学与实践实训环节日益紧密，但现有的教学平台往往将课程管理、作业评测和实训实验功能分散在不同系统中，缺乏统一的教学流程支撑和成绩评价闭环。本项目旨在构建一个集课程管理、在线学习、作业自动评测、实训实验、成绩评价与教学分析于一体的综合性教学平台。

**开发团队与运行环境：** 本项目由北京航空航天大学软件学院大二学生团队承担开发工作，采用前后端分离的 B/S 架构。后端基于 Spring Boot 框架，前端采用 Vue 3 + TypeScript 技术栈，数据存储以关系型数据库为核心，部署环境面向 MySQL，开发和测试环境可使用 H2 的 MySQL 兼容模式。LAB/HWK 代码评测通过可替换的 Fake/Docker 沙箱执行器完成，Redis、OpenAPI 自动生成等能力作为扩展设计保留。平台运行于标准服务器环境，客户端通过现代浏览器访问。

**项目里程碑：**
- 2026 年 4 月 26 日：完成《软件需求规格说明书》（SRS）
- 2026 年 5 月 10 日：完成《软件概要设计说明书》（本文档）
- 2026 年 5 月 24 日：完成《软件详细设计说明书》

### 1.3 定义

| 术语/缩写 | 定义 |
|-----------|------|
| AUTH | 用户权限与平台安全模块，负责用户注册登录、角色权限管理、统一身份认证和审计日志 |
| CRS | 课程与教学资源模块，负责课程创建与管理、章节目录、教学资源上传和选课准入 |
| LRN | 学习过程与通知提醒模块，负责学习行为记录、学习进度跟踪和站内通知生成、查询与状态管理 |
| LAB | 实训实验模块，负责实验任务管理、学生代码提交、Docker 沙箱自动评测和实验报告 |
| HWK | 作业与自动评测模块，负责作业创建发布、学生提交、客观题/代码题自动评测和教师批阅 |
| GRD | 成绩评价与教学分析模块，负责成绩项配置、成绩汇总、总评计算、成绩发布和教学分析 |
| Bearer 访问令牌 | AUTH 模块签发并由前端通过 Authorization 头携带的会话令牌；JWT 可作为令牌格式扩展 |
| RBAC（Role-Based Access Control） | 基于角色的访问控制模型，通过角色来管理用户对系统资源的访问权限 |
| RESTful API | 遵循 REST 架构风格设计的 Web API，使用 HTTP 方法（GET/POST/PUT/DELETE）操作资源 |
| Docker 沙箱 | 基于 Docker 容器技术的代码运行隔离环境，用于安全执行学生提交的代码并进行评测 |
| IO 比对 | 通过比较程序输出（Output）与预期输出（Expected Output）来实现代码自动评测的方法 |
| WebSocket | 一种在单个 TCP 连接上实现全双工通信的协议，可作为站内消息推送的实现方式之一 |
| SSE（Server-Sent Events） | 服务器推送事件技术，作为 WebSocket 的备选方案用于服务端向客户端推送数据 |
| Redis | 高性能内存键值数据库，可作为热点数据、通知未读计数或会话扩展缓存；本版本运行不依赖 Redis |
| MVC（Model-View-Controller） | 后端分层架构模式，将数据模型、视图展示和业务控制逻辑分离 |
| MVVM（Model-View-ViewModel） | 前端分层架构模式，通过 ViewModel 实现视图与数据模型的双向绑定 |
| 课程资源（Course Resource） | 指教师上传并绑定至课程章节的教学材料，包括视频、课件、PDF、实验指导书、外部链接等 |
| 课程成员角色（Course Member Role） | 指用户在课程中的身份类型，包括教师、助教、学生，不同角色决定资源管理、作业管理等权限范围 |
| 统一错误码（Unified Error Code） | 指系统各模块采用统一的接口返回状态码标准，用于测试验证、前后端联调和异常追踪 |
| 评测执行器 | 负责执行代码编译、运行和测试用例比对的基础组件，LAB 和 HWK 模块共享评测服务抽象，可按环境选择 Fake 或 Docker 实现 |

## 2 系统需求概述

### 2.1 需求规定

"在线教学与实训平台"面向高校教学场景，服务于学生、教师和管理员三类核心用户角色，提供从课程创建、资源管理、作业布置到实验实训、成绩评价的完整教学闭环。系统的核心输入输出项目和功能性能要求如下：

**主要输入：**
- 教师：课程信息、教学资源文件、作业/实验任务配置、测试用例、评分标准、公告内容
- 学生：注册/登录凭证、作业/实验提交内容（文本、代码、文件）、客观题答案、成绩异议申请、通知偏好设置
- 管理员：用户管理操作、角色权限配置、平台配置参数
- 系统：来自 AUTH 模块的认证令牌、来自 CRS 模块的课程成员数据、来自 LAB/HWK 模块的评分结果

**主要输出：**
- 页面展示：课程列表、章节目录、学习进度、通知消息、作业/实验详情、评测结果、成绩报表、统计分析图表
- 接口返回：JSON 格式的业务数据、认证令牌、分页列表、操作结果状态
- 数据持久化：用户数据、课程数据、提交记录、评测记录、成绩记录、审计日志
- 站内消息：本版本通过数据库通知表落库并由页面刷新或可配置轮询查询；模块间业务事件包括作业发布、成绩发布等

**功能需求覆盖范围：** 系统共包含六大功能模块，涵盖 40 项功能需求（FR-*）和 30 项非功能需求（NFR-*），具体分布如下：

| 模块 | 功能需求数量 | 非功能需求数量 | 核心能力 |
|------|------------|--------------|---------|
| AUTH | FR-UA-01 ~ FR-UA-07（7项） | NFR-UA-01 ~ NFR-UA-05（5项） | 用户注册登录、角色权限管理、统一鉴权、审计日志 |
| CRS | FR-CR-01 ~ FR-CR-06（6项） | NFR-CR-01 ~ NFR-CR-05（5项） | 课程创建管理、章节资源、选课准入、成员管理、公告与基础信息 |
| LRN | FR-LN-01 ~ FR-LN-06（6项） | NFR-LN-01 ~ NFR-LN-05（5项） | 学习任务中心、进度记录、通知落库与刷新、定时提醒 |
| LAB | FR-LAB-01 ~ FR-LAB-08（8项） | NFR-LAB-01 ~ NFR-LAB-05（5项） | 实验创建发布、提交版本、自动评测、教师评分、统计查询 |
| HWK | FR-HWK-01 ~ FR-HWK-06（6项） | NFR-HWK-01 ~ NFR-HWK-05（5项） | 作业创建发布、学生提交、自动评测、教师批阅重评 |
| GRD | FR-GR-01 ~ FR-GR-07（7项） | NFR-GR-01 ~ NFR-GR-05（5项） | 成绩项配置、成绩汇总总评、成绩发布异议、教学分析 |

**编号归一说明：** 本文档以同目录《软件需求规格说明书》（SRS）为需求基线，课程与学习通知模块统一使用 `FR-CR-*`、`FR-LN-*`、`NFR-CR-*`、`NFR-LN-*` 编号。编号归一不改变课程、学习、通知、接口、数据和流程设计信息的归属。

### 2.2 业务目标

本平台的业务目标是构建一个覆盖教学全流程的在线教学支撑系统，实现以下核心业务价值：

**教学流程闭环：** 实现从"教师创建课程 → 学生选课学习 → 教师布置作业/实验 → 学生提交 → 系统自动评测 → 教师批阅 → 成绩汇总发布 → 教学分析反馈"的完整教学闭环，打通教学各环节的数据流。

**实践能力培养：** 通过 LAB 模块提供的 Docker 沙箱代码评测环境和 HWK 模块提供的自动评测能力，为学生编程类课程提供在线编写、提交、编译运行、测试用例比对的完整实践训练环境，有效支撑程序设计类课程的实践教学。

**教学效率提升：** 通过客观题自动评分、代码自动评测、成绩自动汇总计算等功能，显著减少教师在重复性评分和数据统计工作上花费的时间，使其能够更多地关注教学内容设计和教学指导。

**教学过程可追溯：** 通过学习行为记录、提交历史管理、评测记录留存、成绩变更审计、安全审计日志等机制，实现教学全过程的可追溯、可分析，为教学改进提供数据支撑。

### 2.3 运行环境

#### 2.3.1 设备

**服务端设备：**
- 服务器：标准 x86_64 架构服务器，建议配置 4 核 CPU、8GB 以上内存、100GB 以上磁盘空间
- 网络：支持 TCP/IP 协议的局域网或互联网环境
- Docker 环境：LAB 模块的代码评测需要 Docker 运行环境，建议独立部署或使用轻量级容器运行时

**客户端设备：**
- 学生/教师/管理员通过现代浏览器访问（Chrome 90+、Firefox 88+、Edge 90+）
- 屏幕分辨率建议 1280×720 及以上，支持响应式布局适配

### 2.4 设计约束

**技术选型约束：**
- 后端必须使用 Spring Boot 框架，遵循 MVC 分层架构（Controller → Service → Repository）
- 前端必须使用 Vue 3 + TypeScript + Vite 技术栈，遵循 MVVM 架构
- 部署数据库使用 MySQL 8.0；开发和测试可使用 H2 的 MySQL 兼容模式；数据访问层采用 Spring JDBC Repository/DAO，Mapper 命名仅作为数据访问接口或占位边界
- 接口风格统一采用 RESTful API，响应格式遵循全局统一结构 `{ code, message, data }`

**架构设计约束：**
- 前后端分离部署，通过 HTTP/HTTPS 通信
- 统一身份认证：所有需认证接口均通过 AUTH 模块签发的 Bearer 访问令牌和后端认证上下文进行鉴权
- 模块间数据交互通过标准接口调用和事件机制实现，模块内部实现互相不可见
- 代码评测服务（LAB/HWK 共享）采用应用内异步执行器或任务队列抽象，评测过程不阻塞提交接口响应

**团队与时间约束：**
- 开发团队为 6 名大二本科生，需在详细设计阶段前完成概要设计
- 本版本设计侧重核心功能可实现性，不扩展为完整在线判题平台、校级教务系统或复杂 AI 分析系统
- 每个模块由指定的模块负责人负责设计，概要设计负责人统一协调

**接口规范约束：**
- 所有 API 接口路径采用 `/api/v1` 前缀
- 分页查询统一使用 `page` 和 `size` 参数
- 错误码需各模块统一定义，便于测试验证和前后端联调
- 接口文档以最终提交设计文档中的接口表为基线，Swagger/OpenAPI 可作为后续自动生成扩展

#### 2.5.1 用户权限与平台安全（AUTH）

**模块概述：** AUTH 模块是平台的基础设施模块，负责用户注册登录、会话管理、角色权限管理和统一身份认证，为所有业务模块提供可信的用户身份来源和权限校验基础。

##### FR-UA-01 用户注册与登录（P0）

| 属性 | 描述 |
|------|------|
| 需求编号 | FR-UA-01 |
| 优先级 | P0（必须实现） |
| 涉及角色 | 学生、教师、管理员 |
| 核心功能 | 用户通过学号/工号、手机号、邮箱或系统指定账号完成注册与登录，登录成功后获得有效会话或访问令牌。 |
| 设计要点 | ① 注册时保存账号、用户类型、联系方式、密码哈希和账号状态，账号标识应保持唯一。<br>② 登录时先校验账号是否存在、密码是否匹配、账号状态是否正常，再创建会话或令牌。<br>③ 登录成功后返回用户基础信息、角色列表、权限摘要和令牌有效期。<br>④ 退出登录时应作废当前会话或令牌，避免退出后继续访问需认证资源。<br>⑤ 登录失败时不暴露账号是否存在等敏感细节，可统一提示账号或密码错误。 |

##### FR-UA-02 角色管理与权限分配（P0）

| 属性 | 描述 |
|------|------|
| 需求编号 | FR-UA-02 |
| 优先级 | P0（必须实现） |

| 设计要点 | ① 学生端展示提交时间、提交状态、评测状态、通过情况、反馈摘要、教师评语和已发布成绩。<br>② 若教师尚未发布成绩，学生只能查看被允许公开的评测反馈，不显示未发布最终分数。<br>③ 教师端按 CRS 当前活跃学生统计单次作业的总人数、已提交/未提交、可自动评测/已评测/待评测、已批阅/待批阅、已计分数量、平均分、最高分、最低分和生成时间；历史版本、删除记录、REJECTED 和非当前课程学生排除。<br>④ 分数分布固定为 `0-59`、`60-69`、`70-79`、`80-89`、`90-100`，按 `effectiveScore = finalScore ?? autoScore` 和 `effectiveScore / totalScore × 100` 归一化后分桶；无分数不入桶，`scoredCount` 等于五档合计。评测完成率使用 `evaluatedCount / autoEvaluableCount`，TEXT/FILE 的 NONE 不计为待评测。<br>⑤ 未提交名单由统计接口分页返回，待评测/待批阅名单由提交列表接口的 `attention` 参数分页返回；三者均保持稳定排序和 URL 可恢复。<br>⑥ 结果展示需区分自动得分、教师评分和最终得分。<br>⑦ 成绩发布后，HWK 向 LRN 发送成绩发布通知事件，并向 GRD 提供成绩数据。 |

HWK 的统计边界是“单次作业、固定五档和三类跟进名单”；课程级、跨作业、自定义区间、趋势和统计快照仍由 GRD 负责。HWK 不创建或维护 GRD 的课程统计快照。

#### 2.5.6 成绩评价与教学分析（GRD）

**模块概述：** GRD 模块是平台教学评价闭环的终端模块，负责成绩项配置、成绩汇总与总评计算、教师成绩管理与发布、学生成绩查询、班级成绩统计分析以及成绩异议复核功能。GRD 从 LAB 和 HWK 模块读取评分数据，完成课程级成绩归集和总评计算。

| NFR-HWK-05（可测试性） | 本模块核心流程应便于单元测试、接口测试和系统演示测试 | 自动评测服务应设计为可 Mock 的接口；现有 HWK 回归加上 TC-HWK-20 ~ TC-HWK-27 覆盖 FILE 附件生命周期、白名单、所有权、原子绑定/补偿、清理、历史安全视图、受控下载与前端状态；MAN-HWK-012 在 1440×900 与 390×844 的真实浏览器证据必须单独回填，不以自动化结果替代 |

#### 2.6.6 GRD 非功能需求

| 需求编号 | 需求描述 | 设计约束 |
|---------|---------|---------|
| NFR-GR-01（可靠性） | 成绩汇总、计算、发布和统计分析流程必须具有明确状态，避免成绩状态不一致 | 成绩项、成绩记录、发布记录、变更记录分表保存；来源成绩同步和总评计算在事务边界内更新 |
| NFR-GR-02（性能） | 小并发演示环境下成绩查询和统计分析需在规定时间内返回 | 课程成绩总表分页查询在 5 秒内返回；学生个人成绩查询在 3 秒内返回 |
| NFR-GR-03（可追踪性） | 成绩项定义、成绩计算、成绩发布、成绩修改和成绩复核过程均应保留记录 | 成绩记录保存来源模块、来源任务编号；已发布成绩修改必须记录修改前后值和原因 |
| NFR-GR-04（安全性） | 学生只能访问本人已发布成绩，教师只能访问授权课程成绩 | 所有接口均需 Bearer 访问令牌和认证上下文鉴权；学生查询强制使用当前登录用户过滤 |
| NFR-GR-05（可测试性） | 关键功能和异常场景需可稳定复现并映射测试项 | 未发布不可见、规则错误、来源缺失、已发布成绩修改留痕等异常场景可由测试数据构造 |

#### 2.7.3 技术架构要点

**后端分层架构（MVC）：**
- Controller 层：接收 HTTP 请求，参数校验，调用 Service 层，返回统一响应格式
- Service 层：核心业务逻辑，事务管理，模块间调用
- Repository/Mapper 层：数据访问，当前以 Spring JDBC/Repository 为主，保留 Mapper 抽象边界
- 统一异常处理器：全局捕获和处理业务异常

**前端分层架构（MVVM）：**
- View 层：Vue 3 单文件组件与统一应用外框
- ViewModel 层：Vue 3 组合式 API、轻量页面状态和本地存储辅助
- Model 层：TypeScript 类型定义、模块 API wrapper 和统一 HTTP 调用
- 路由守卫：基于权限的页面访问控制

**通信与缓存策略：**
- 前后端通信：HTTP/HTTPS + RESTful API + JSON
- 站内消息：本版本使用数据库通知表落库，前端通过页面加载、手动刷新或可配置轮询查询通知列表与未读数；WebSocket/SSE 推送仅作为后续扩展
- 缓存策略：本版本以数据库查询、分页和必要的本地状态为主；Redis 可作为后续热点数据和未读通知数缓存扩展
- 异步处理：代码评测采用应用内异步执行器或任务队列抽象执行

**数据所有权与信息隐藏：**
- AUTH 拥有用户、角色、权限、会话和审计日志数据；其他模块只通过认证上下文或授权接口获取当前用户身份，不直接修改 AUTH 数据。
- CRS 拥有课程、章节、资源、课程成员和公告数据；LAB、HWK、GRD 只保存 `course_id`、`chapter_id`、`user_id` 等逻辑引用，通过 CRS 接口校验课程成员关系和课程权限。
- LAB 与 HWK 分别拥有实验、作业、提交、评测和评分数据，二者不直接访问对方业务表；共享评测能力抽象为独立评测执行器基础设施。
- GRD 拥有成绩项、成绩记录、总评、发布记录、变更记录、异议申请和统计快照数据；来源成绩通过 LAB/HWK 的接口或事件同步形成快照。
- 数据库设计中出现的跨模块编号均表示逻辑引用。详细设计阶段可在同库部署中增加物理外键，但不得以物理外键替代模块 API、事件和权限校验契约。

| 节点 | 主要职责 | 通信关系 |
|------|---------|---------|

### 3.2 外部接口设计（API）

> 本节按模块分别描述各模块对外提供的 RESTful API 接口和跨模块事件接口。所有接口路径统一采用 `/api/v1` 前缀，需认证接口均需携带 AUTH 签发的 Bearer 访问令牌，响应格式遵循 `{ code, message, data }` 统一结构。

#### 3.2.1 AUTH 模块接口

**认证与会话接口：**

| 编号 | 接口 | 方法 | 主要参数 | 返回内容 | 说明 |

本平台的运行模块组合按用户角色和使用场景划分，描述不同角色在使用平台时的典型模块组合路径。

**学生角色典型流程：**

学生登录平台后，首先通过 AUTH 模块完成身份认证，进入学生工作台。在 CRS 模块中浏览和加入课程，查看课程章节和教学资源。在 LRN 模块中跟踪学习进度、接收通知提醒。在 HWK 模块中查看和提交作业、查看评测结果和教师反馈。在 LAB 模块中查看实验要求、提交代码、查看 Docker 沙箱自动评测结果、提交实验报告。在 GRD 模块中查看已发布的个人成绩和成绩项明细，如有异议可提交复核申请。

涉及的模块组合：AUTH → CRS → LRN → HWK/LAB → GRD

**教师角色典型流程：**

教师登录后通过 AUTH 模块完成身份认证。在 CRS 模块中创建和管理课程、章节、资源和公告，管理课程成员。在 HWK 模块中创建和发布作业、配置测试用例、批阅学生提交、触发重评。在 LAB 模块中创建和发布实验任务、配置 Docker 沙箱评测参数、查看评测结果、评分实验报告。在 GRD 模块中配置成绩项和权重、同步来源成绩、计算总评、发布成绩、查看教学统计分析、处理成绩异议。

涉及的模块组合：AUTH → CRS → HWK + LAB → GRD

**管理员角色典型流程：**

管理员登录后在 AUTH 模块中管理用户账号、分配角色和权限、查看安全审计日志。管理员不直接参与课程教学业务，但可进行课程审核、下架等平台级管理操作。

涉及的模块组合：AUTH（主要）+ CRS（课程审核）

**系统后台运行模块：**

评测执行器作为 LAB/HWK 共享基础能力运行，可按环境选择 FakeSandboxExecutor 或 DockerSandboxExecutor；业务服务通过应用内异步执行器或任务队列抽象触发评测，并将结果回写到提交与评测记录。LRN 模块提供站内消息能力，业务事件先写入通知表，前端通过页面刷新、手动刷新或可配置轮询读取通知与未读数。HWK 模块的截止提醒通过定时任务扫描即将到期的作业并触发通知事件。

涉及的模块组合：评测执行器（HWK/LAB 共享）+ LRN 通知刷新 + 定时任务调度

### 5.2 运行控制

**认证与鉴权控制：**

系统通过 AUTH 模块的统一认证拦截器对所有需认证的 API 请求进行控制。请求到达后端时，拦截器解析 Bearer 访问令牌、校验令牌有效期并查询会话状态。认证通过后，拦截器将当前用户上下文（user_id、roles、permissions）注入请求上下文，供下游业务模块使用。认证失败时返回标准化的未认证错误码（401）或无权限错误码（403）。

**业务流程控制：**

各业务模块在执行关键操作前需完成前置校验。例如 HWK 模块在学生提交作业前需校验：① 用户已登录（AUTH 认证）；② 作业已发布且未关闭（作业状态校验）；③ 学生属于该课程（CRS 成员关系校验）；④ 未超过提交限制（提交次数和截止时间校验）。这些校验通过后才执行业务逻辑和数据库操作。

**数据一致性控制：**

涉及多表更新的操作（如成绩发布）需在数据库事务中完成，保证原子性。模块间数据同步（如 GRD 从 LAB/HWK 同步来源成绩）需记录同步批次和时间点，支持追溯和重试。发布操作需具备幂等保护，避免重复操作导致数据异常。

**异常处理控制：**

系统通过统一异常处理器捕获和处理所有未处理异常。业务异常返回明确的错误码和用户可理解的错误提示，不暴露堆栈信息、SQL 语句、令牌细节等内部信息。评测服务异常时，提交记录保留但评测状态标记为 SYSTEM_ERROR，不影响学生和教师查看提交内容。网络异常时，前端通过本地缓存保存用户操作，联网后自动重试。

### 5.3 运行时间

**响应时间要求：**

| 操作类型 | 响应时间要求 | 说明 |
|---------|------------|------|
| 登录/注册认证 | ≤ 3 秒 | AUTH 模块 |
| 页面加载（列表查询） | ≤ 2 秒 | 分页查询和索引优化；Redis 可作为后续缓存扩展 |
| 作业/实验提交 | ≤ 3 秒 | 异步评测，不等待评测完成 |
| 代码自动评测 | ≤ 60 秒 | 异步执行，基础规模测试用例 |
| 成绩查询（学生） | ≤ 3 秒 | 按 courseId + studentId 索引 |
| 成绩总表查询（教师） | ≤ 5 秒 | 分页查询 |
| 通知列表加载 | ≤ 1 秒 | 首屏加载 |
| 未读红点更新 | 页面加载、手动刷新或轮询后可见 | 通过通知查询接口返回未读数；WebSocket/SSE 推送属于扩展机制 |
| 统计分析计算 | ≤ 5 秒 | 课程级/班级级统计 |

**可用性要求：**

系统在项目演示和验收期间需保持稳定可用。关键功能（登录、提交、查询、发布）不可出现频繁超时或服务不可用情况。单模块异常不应导致整个平台不可用。

**数据量预期：**

本版本系统面向课程项目演示环境，预计数据规模为：用户数百级、课程数十级、作业/实验数百级、提交记录数千级、成绩记录数千级。数据库设计在索引和数据类型选择上已考虑此规模下的查询性能。
